# Observability — Design Decision

**Scope:** structured logging, log correlation, monitoring infrastructure — from the modulith on bare metal through extraction to microservices.

**Status:** logging contract lives in `commons`; monitoring stack is deployment-specific.

---

## 1. Logging stack — `commons` owned

**SLF4J + Logback** (Spring Boot default) with **Logstash Logback Encoder** (`net.logstash.logback:logstash-logback-encoder`) for structured JSON output. One additional dependency beyond Spring Boot starters.

`commons` provides three things:

| Component | Location | Purpose |
|---|---|---|
| `logback-base.xml` | `commons/src/main/resources` | Base Logback config — JSON appender to stdout, log level defaults, included by every module's `logback-spring.xml` via `<include>` |
| `RequestContextFilter` | `commons.web` | Servlet filter — stamps `traceId`, `requestId`, `userId`, `module` into MDC on every incoming HTTP request; clears on response |
| `MdcTaskDecorator` | `commons.async` | `TaskDecorator` for Spring's `TaskExecutor` — copies MDC context to async threads so event listeners inherit the originating request's trace context |

### Log format (contract)

Every log line is a single JSON object to stdout:

```json
{
  "timestamp": "2026-09-05T10:00:00.123Z",
  "level": "INFO",
  "logger": "com.fold.backend.matching.LikeService",
  "module": "matching",
  "traceId": "8f2c1a3d4b5e4c6f9a0d1e2f3a4b5c6d",
  "requestId": "req-7f3a1c4e",
  "userId": "9f3a1c4e-2b7d-4a81-9c5e-8d2f0a6b3c11",
  "message": "Like created",
  "context": { "like_id": "d7c4e6a8-...", "target_id": "7a2b9c1d-..." }
}
```

| Field | Source | Notes |
|---|---|---|
| `timestamp` | Logback | ISO-8601 UTC |
| `level` | Logback | `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR` |
| `logger` | Logback | Fully qualified class name |
| `module` | MDC | Derived from the request path prefix (`/users/...` → `users`, `/matching/...` → `matching`) by `RequestContextFilter` |
| `traceId` | MDC | **W3C Trace Context format** — 32-char lowercase hex. Generated by `RequestContextFilter` if no incoming `traceparent` header; otherwise extracted from it. W3C format from day 1 so OpenTelemetry adoption requires zero log format changes. |
| `requestId` | MDC | Short request-local id for grouping log lines within a single HTTP request |
| `userId` | MDC | `oid` claim from the JWT principal; absent for unauthenticated requests (e.g. JWKS fetch, health check) |
| `message` | Logger call | Human-readable event description |
| `context` | Structured args | Business-relevant key-value pairs passed via SLF4J's structured argument API or Logstash markers — not string-interpolated into `message` |

### Log level policy

| Level | When to use |
|---|---|
| `ERROR` | Unrecoverable failure — request cannot be fulfilled, data integrity risk, external dependency down. Always includes exception + stack trace. |
| `WARN` | Recoverable but unexpected — retry succeeded, fallback activated, validation rejected a request. |
| `INFO` | Business events — user registered, like created, match formed, gate evaluated, event published/consumed. One per significant state change; not per helper call. |
| `DEBUG` | Internal flow — cache hit/miss, query parameters, intermediate decisions. Off in production by default. |
| `TRACE` | Framework-level — HTTP headers, full payloads, SQL. Off in production. |

**Production default:** `INFO` for `com.fold.backend`, `WARN` for framework packages. Adjustable per module at runtime via Spring Boot actuator (`/actuator/loggers`).

### Correlation across async events

In the modulith, async events (Spring `@ApplicationModuleListener`) run on a `TaskExecutor`. The `MdcTaskDecorator` copies the publishing thread's MDC snapshot to the listener thread, so consumed events carry the originating request's `traceId`. If an event is retried from the persistent event publication store (no originating thread), a new `traceId` is generated.

```
HTTP request (traceId=abc123)
  → UserService.register()          [MDC: traceId=abc123, module=users]
    → publish UserRegistered         [same thread, same MDC]
      → MatchingListener.onUserRegistered()  [async thread, MDC copied: traceId=abc123, module=matching]
      → NotificationsListener.on...()        [async thread, MDC copied: traceId=abc123, module=notifications]
```

### What NOT to log

- Credentials, tokens, passwords, API keys — never, at any level
- Full request/response bodies in production — `DEBUG`/`TRACE` only
- PII beyond `userId` — no email, name, DOB, location in log lines
- Per-iteration loop noise — log the outcome, not every step

## 2. Monitoring — V1 (bare metal, single container)

The app runs as a Docker container on bare metal, logging structured JSON to **stdout** (12-factor app convention).

### Stack: Loki + Grafana

| Component | Role | Resource footprint |
|---|---|---|
| **Grafana Loki** | Log aggregation + storage. Receives logs via Docker log driver or Promtail sidecar. Indexes by labels (`module`, `level`, `traceId`), stores compressed log chunks. | ~256 MB RAM, disk scales with retention |
| **Grafana** | Dashboard + query UI. LogQL queries against Loki — filter by module, level, traceId, userId, time range. Alerting rules for `ERROR` spikes. | ~128 MB RAM |
| **Promtail** (sidecar) | Scrapes container stdout, adds labels, pushes to Loki. Alternative: Docker's Loki log driver (simpler, fewer features). | ~64 MB RAM |

All three run as containers alongside the app in a single `docker-compose.yml`. Total overhead: ~512 MB RAM.

### Common queries (LogQL)

```logql
# All errors in the last hour
{module=~".+"} | json | level="ERROR"

# Trace a specific request across modules
{module=~".+"} | json | traceId="8f2c1a3d4b5e4c6f9a0d1e2f3a4b5c6d"

# All ratio gate evaluations
{module="ratio"} | json | message=~".*gate.*"

# Errors for a specific user
{module=~".+"} | json | level="ERROR" | userId="9f3a1c4e-..."
```

### Alerting (V1, minimal)

| Alert | Condition | Channel |
|---|---|---|
| Error spike | > 10 `ERROR` lines in 5 min | Email (Grafana SMTP, same `JavaMailSender` config as notifications) |
| App down | No log lines for 2 min | Email |

### Log retention

V1: **30 days** on local disk. Loki's compaction keeps storage manageable for a single-app workload. Older logs are dropped — no archival in V1.

## 3. Future — microservices + OpenTelemetry

When the modulith is extracted to separate services, three things change: traces span HTTP boundaries, logs need correlation across services, and metrics become per-service.

### Migration path

| Concern | Modulith (now) | Microservices (later) |
|---|---|---|
| **Trace propagation** | MDC within the JVM + `MdcTaskDecorator` for async | OpenTelemetry Java Agent auto-instruments HTTP clients/servers, propagates `traceparent` header (W3C Trace Context) |
| **Log correlation** | `traceId` in MDC (W3C format, 32-char hex) | Same field, same format — OpenTelemetry agent populates it automatically from the distributed trace |
| **Trace visualization** | Loki trace-by-id search (flat log lines) | **Grafana Tempo** (distributed trace backend) — waterfall view of spans across services, linked to Loki logs via `traceId` |
| **Metrics** | Spring Boot Actuator (`/actuator/metrics`) | Micrometer → OpenTelemetry exporter → **Prometheus** + Grafana dashboards |
| **Log shipping** | Promtail → Loki (single host) | Promtail/OpenTelemetry Collector → Loki (may move to managed instance or cluster) |

### What to do now to make migration painless

1. **W3C trace format from day 1** — already specified above. When the OpenTelemetry agent is added, it sees the same `traceId` field and populates it with real distributed trace IDs. Zero log format changes.
2. **`traceparent` header extraction in `RequestContextFilter`** — if an incoming request carries a `traceparent` header (W3C standard), extract and use its `trace-id` instead of generating a new one. This is a no-op today (no upstream sets it) but means the filter is OpenTelemetry-ready without modification.
3. **Structured context fields** — business data in `context` (not interpolated into `message`) means queries work identically before and after the migration.
4. **Grafana stays** — Loki, Tempo, and Prometheus all feed into Grafana. The dashboards evolve; the platform doesn't change.

### What NOT to do now

- Don't add the OpenTelemetry agent or SDK — it's unnecessary overhead in a single-process modulith where all calls are in-memory.
- Don't introduce Kafka/message-bus log shipping — Promtail → Loki is sufficient for one host.
- Don't build distributed tracing dashboards — there's nothing to distribute yet.
- Don't add Prometheus/metrics exporters — Spring Boot Actuator is enough for V1 ops visibility.

## 4. Spring Modulith observability integration

`spring-modulith-observability` auto-instruments module boundaries via Micrometer's `ObservationRegistry`. This is framework-provided — no custom instrumentation needed.

### What it observes automatically

| Interaction | Observation | What you get |
|---|---|---|
| Sync client calls (e.g. `UserClient.getPublicProfile()`) | Micrometer span per call | Caller module, target module, method, duration, success/failure |
| Event publication (`applicationEventPublisher.publishEvent()`) | Observation on publish | Event type, producer module, timestamp |
| Event consumption (`@ApplicationModuleListener`) | Observation on listener execution | Event type, consumer module, duration, success/failure/retry |
| Failed event retries | Observation on retry attempt | Retry count, original failure, time since first attempt |

These observations feed into:
- **V1:** Spring Boot Actuator metrics (`/actuator/metrics`) — module call counts, event processing times, failure rates
- **Later:** Micrometer → OpenTelemetry bridge exports the same observations as distributed traces + Prometheus metrics with zero code changes

### How it interacts with our custom logging

`spring-modulith-observability` handles **module boundary observation** (spans, metrics). Our custom code handles **request context propagation** (MDC fields for structured log lines). They don't overlap:

```
HTTP request arrives
  │
  ├─ RequestContextFilter (ours)         → stamps MDC: traceId, requestId, userId, module
  ├─ Spring Security                     → JWT verification
  ├─ Controller → Service
  │    ├─ SLF4J log lines                → carry MDC fields automatically (ours)
  │    └─ UserClient.getPublicProfile()  → Modulith creates Micrometer observation (framework)
  │
  └─ Event publish
       ├─ Modulith observes publication  → (framework)
       └─ Async listener thread
            ├─ MdcTaskDecorator (ours)   → copies MDC from publisher thread
            ├─ Modulith observes consumption → (framework)
            └─ SLF4J log lines           → carry copied MDC fields (ours)
```

### Dependency

The `MdcTaskDecorator` must wrap the same `TaskExecutor` that Spring Modulith uses for `@ApplicationModuleListener`. This is configured once in the application's main config (not in commons):

```java
@Configuration
class AsyncConfig {
    @Bean
    TaskExecutor applicationTaskExecutor(MdcTaskDecorator decorator) {
        var executor = new ThreadPoolTaskExecutor();
        executor.setTaskDecorator(decorator);
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("modulith-event-");
        return executor;
    }
}
```

## 6. Non-rules

- Every module logs through SLF4J — no direct `System.out.println`, no custom log frameworks.
- Log format is JSON in all environments (including local dev) — consistency over readability; use `jq` for local inspection.
- `RequestContextFilter` is registered at the highest precedence (before auth) so that even auth failures carry a `traceId`.
- Health check and actuator endpoints log at `DEBUG` to avoid noise.
- Module boundary observations are framework-managed — never create manual Micrometer observations for inter-module calls.
